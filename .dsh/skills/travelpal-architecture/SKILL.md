# TravelPal 架构编排哲学

本 skill 承载 TravelPal 的**架构思想**，不是操作手册。判断一个改动怎么做时，先回到这里的每一条原则；具体"哪些代码放哪层、重复怎么抽"的方法见 `references/`。

## 这个 skill 管什么（边界）

- **管**：目录怎么拆、路由怎么分层、公共模块怎么抽、新代码放哪层、文件该不该拆。
- **不管**：注释怎么写、代码风格、docstring、接口清单、VNS 引擎写法——那是 `travelpal-coding`。

## 三条心法（任何决策前先问）

1. **先探索，再决策，后动手。** 加/改/删功能前，必须先看清现有结构，绝不上手就写。
2. **新增默认沿用现有分层，不新造一层。** 除非探索后确有必要。
3. **api 只做接入，业务下沉。** 不要在路由里写业务逻辑。

## 十条原则

### 一、演进式架构
按多 Agent 设计、按单 Agent 执行；**一次只动一个轴**；占位优于提前引；用**度量**说话，不凭感觉。
**屎山是"先这样，后面再改"累计出来的（熵增），对抗它不是靠一次重写，而是靠演进式架构**：旧系统旁建新模块（如 `engine/orchestrator.py`），**拦截入口 → 逐步替换实现 → 绞杀退役旧代码**（如 CA/VNS → OR），风险隔离、可持续交付。做法见 `references/evolution.md`。

### 二、深度解耦
依赖方向单一（domain 零依赖 → infrastructure 只依赖 domain → api 只做接入）；**接口先行、实现可插拔**；防腐层真防腐。

### 三、文件不可重复
**同一逻辑只有一处定义。** 任何"两份文件共同维护一个逻辑"都是腐化——那逻辑应被提取为公共模块。

### 四、全是精华
无死代码、无失效样式、无一份"备份副本"。每个文件都必须不可替代。

### 五、自写优先
能自写证明够用就不换框架。**白盒可读 + 实现简单 + 依赖少 + 轻量 + 确有大用**才引框架（如 langgraph 之于编排、markdown-it 之于 md 解析）。

### 六、拆分看"变化是否独立"，不看长度
**文件长不是拆分的理由。** 拆不拆看"未来改动是否独立"：改这个不改那个 → 拆；每改都牵连 → 硬拆反而制造跨文件耦合。routes.py 就是"长但内聚，不该拆"的典型。

### 七、Rule of Three：第 3 次出现才抽象
给原则三加护栏：同一逻辑出现在 2 处 → 可忍，先标注；**第 3 处 → 抽公共模块**。这样抽象有明确收益，不会把 5 行代码也抽成模块（那是另一种腐化）。

> **与原则三的衔接**：发现第 2 次出现时，在代码中加一条 TODO 注释「此处与 XXX 重复，第 3 次出现时抽取」——**标注但不行动**，等第 3 次再统一抽取。标注本身已降低认知负荷，因为重复是被识别出来的，而不是被忽略的。

### 八、架构的受众是"未来的你 + AI"，认知负荷是度量
拆分/解耦的真正价值不是"技术正确"，而是**降低认知负荷**。判断架构好坏问"我要改这个会花多久"，而不是"它符不符合教科书"。

### 九、实现可以换，接口/结构/状态保持单一来源
给原则三划边界：**接口 / 数据结构 / 全局状态**值得单一来源（OpenAPI、TOOL_REGISTRY）；**纯实现细节**不值得（因为实现本来就该换）。别把"无重复"用错地方。

> **判别标准：消费者数 > 1 才值得提取。** 多个消费者依赖同一份定义的，才值得单一来源——如 API 契约（前后端共用）、工具注册表（Agent 与 MCP 共用）、全局状态（多组件读取）、数据库 Schema（迁移脚本与 ORM 共用）。**只有一个消费者**的定义，不值得被单独提取（那是过度抽象）。

### 十、文档是独立的生命体，不是代码的附庸
文档有自己的生命周期，由自身更新日期标注"生命"。**文档可能落后于代码，但落后 ≠ 失效——它仍是它所覆盖时间段的"当时事实"**。改动代码不必强求文档即时跟进，但要让文档如实记录它标注的那个时刻；当代码演进到旧文档不再是"事实"时，用一次独立的文档更新完成交接，而非假装它从未存在。

## 决策流程（快速版）

```
① 探结构   → 读现有目录树 + 关键入口（backend/api/server.py、frontend/router/、services/api.ts）
② 找需求   → 用户要加的东西本质是什么（纯算法/外部IO/业务编排/LLM对话/HTTP接入/页面/组件/状态）
③ 定位层   → 对照 references/backend.md 或 references/frontend.md 的职责边界判断归属
④ 复用检查 → 有没有现成公共模块？同一逻辑是否已出现第 2/3 次？
⑤ 决策确认 → 给出"改动清单"（哪个放哪、新不新建目录、动不动已有层），交给用户确认后再动手
```
