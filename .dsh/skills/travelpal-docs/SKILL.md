# 项目文档维护方法论

本 skill 管理 TravelPal **全项目所有 `.md` 文档**的组织、生命周期、导航、构建。它是"方法"，不是"内容"——规范/模板在 `assets/`。

## 三条心法

1. **文档是独立生命体，不是代码附庸。** 靠修改记录日期标注生命；落后 ≠ 失效，它是所覆盖时间段的"当时事实"。
2. **元文档不进 docs/。** "关于文档的文档"（README/TEMPLATE）收敛到本 skill 的 `assets/`，docs/ 只留纯内容文档。
3. **入口文档 = 接口，本 skill 是唯一修改者。** 根目录的入口文档对**其他 skill 是"接口"**——它们只管**引用**当输入，不在乎怎么改（"只用接口，不关心实现"）；**本 skill 才负责改**（实现）。单一维护者，避免多处写同一份。

## 一、文档分类与职责边界（核心）

项目里的 `.md` 按**文档职责**分类，不是按文件名。写/改任何 md 前，先判断它属于哪类——**分类决定结构、生命周期、归属地**。

| 文档类型 | 职责 | 结构特征 | 归属 |
|---------|------|---------|------|
| **ADR（决策记录）** | 只记「选了什么、为什么、代价」，**不含演进细节** | 一文档一重大决策；元信息/状态/执行摘要/决策/备选/后果/复审 | `docs/ADR/` |
| **design（规划/设计蓝图）** | 演进路线图、多决策索引、组件状态跟踪——"往哪走" | 元信息/执行摘要/背景/总体目标/分阶段路线图/各轴设计/状态跟踪 | `docs/design/` |
| **product（产品/哲学）** | 做成什么、为什么存在、产品定位与方向 | 读者指南/定位/愿景/路线图 | `docs/product/` |
| **structure（结构详解）** | 某层架构"是什么样" | 架构总览/目录结构/数据流/维护契约 | `docs/structure/` |
| **handoff（交接文档）** | 会话上下文快照：本会话做到哪、下一步做什么 | YAML frontmatter（task/status/date/version）+ 上一段/决定坑/下一步 | `docs/handoff/` |
| **入口文档** | 项目门面：产品介绍、常驻硬规则、C4 图 | README（门面）/ AGENTS（常驻底线）/ ARCHITECTURE（C4） | 根目录 |
| **特别文档（草稿本）** | 待做想法草稿（inbox），**不是常规内容文档** | 最简、一条一想法、讨论可选；git 忽略、不自动读 | `docs/inbox.md` |

**分类判断（写前先问）**：
- 是"**我选了什么**"且不会反复演进 → **ADR**。
- 是"**我要往哪走**"、含多阶段/多轴/状态跟踪 → **design**。
- 是"**做成什么**"、面向产品/用户 → **product**。
- 是"**某层是什么样**"的静态详解 → **structure**。
- 是"**本会话做完没、下一步做什么**"的上下文快照 → **handoff**。

## 二、全项目 md 文档地图（按角色，不含具体文件名）

> 本 skill 只描述**文档角色**，不硬编码具体文档/文件名——项目文档会演进，skill 不背"状态快照"。

| 角色 | 放哪 | 维护者 |
|------|------|--------|
| 入口文档 | 根目录 | 本 skill（唯一修改者） |
| 决策记录 | `docs/ADR/` | 本 skill（模板见 assets/adr-template） |
| 规划/设计蓝图 | `docs/design/` | 本 skill |
| 产品/哲学 | `docs/product/` | 本 skill |
| 结构详解 | `docs/structure/` | 本 skill（模板见 assets/structure-template） |
| 交接文档 | `docs/handoff/` | `session-handoff` skill（本 skill 只定义分类，读写走那个） |
| 版本说明 | `docs/releases/` | 本 skill（内容走 git-release 机制，模板见其 assets） |
| 外部反馈 | `docs/feedback/` | 本 skill（AI/他人评审等原始反馈，只归档不整理） |
| 技能文档 | `.dsh/skills/*/SKILL.md` | `skill-authoring` skill（本 skill 只引用） |
| 文档导航 | `docs/index.rst` | 本 skill（唯一事实源） |
| 前端静态内容 | `frontend/src/content/*.md` | 本 skill |

> **特别文档 · `docs/inbox.md`（独立且特别）**：待做/想法**草稿本**。它**不是**常规内容文档——**git 忽略**、**不自动读**、**不做升级路径**（不整理成任务系统），按需浏览后决定做就在会话提出。本 skill 只标注"它是特别的、别当普通文档处理"，不改它的结构。

> **边界**：`AGENTS.md` 只列"规范指引表"（场景→skill）索引，**不注入规范原文**——规范正文在各 skill 里。本 skill 是 AGENTS.md 的唯一修改者。技能文档（SKILL.md）的写法归 `skill-authoring`，本 skill 只引用不重复。

## 三、文档生命周期（原则十落地）

- **靠修改记录标注生命**：顶部「修改记录」表（日期+变更+动机）是文档"活着"的证据。
- **落后 ≠ 失效**：落后仍代表其标注时间段的事实。别因落后就删——判是"过时"还是"仍是当时事实"。
- **三态**：
  - **当前有效**：内容与代码相符，修改记录日期最近。
  - **已过时（标注）**：内容落后但仍有参考价值（如某版本架构）。index.rst 或文件头标注「内容过时」，保留不删。
  - **已废弃（移除）**：被替代/彻底无用。归档或删，并从 index.rst 移除引用。
- **何时更新 vs 只标注**：代码重构引用了文档 → 更新；只是某版本快照 → 标注过时，不追改。
- **frontmatter 时间戳**：各 md 文档开头用 `---` 块，**date 必须**、`version`/`status` 可选；handoff（交接文档）多一个 **task** 字段。这是文档"生命标记"的机器可读版。
- **AI 判时效**：读任何 md 先扫 `frontmatter` 里的 `date` 字段——一眼知道文档何时写、是否过期，无需全文搜"发布于…"。date 放 frontmatter（位置固定）比放正文（位置不固定）更利于快速判时效。

**翻修前先看现状**：要对文档做大改/翻修前，先读 `docs/handoff/`（上次文档会话做到哪）与 `docs/releases/`（已发布版本与说明），了解当前基线、避免重复或与已发布内容冲突。

## 四、各文档类型规范

上文「文档分类」定义了各类型是什么；本节给出**每一类型怎么写**。四类（ADR / design / product / handoff）各自独立小写，模板收在 assets/。

### 4.1 ADR 文档规范（写"决策记录"，非"实施细节"）

- **一文档一重大决策**；关联度高的子主题同文档分节。
- **新 ADR 用 `assets/adr-template.md`**。
- **核心**：只记「选了什么、为什么、代价」，不记实施细节；正文不含文件路径（路径归「组件状态跟踪」验证列）。
- **追加式**：决策演进用新 ADR 追加，不改写历史。
- **理由充分**：每个选择写「为什么不选其他」——ADR 的核心价值。

### 4.2 design 文档规范（写"规划蓝图"，非"决策记录"）

> 当文档承载"演进路线图 + 多决策索引 + 组件状态跟踪表"时，它属于 design/，**不是 ADR**。**去掉 "ADR-xxx" 编号**，改用规划蓝图结构。

**标准结构**：用 `assets/design-template.md`（不留在 docs/，收敛于此）。

**与 ADR 的关联**：design 文档是**规划蓝图**，ADR 是**决策依据**。design 里提到某个决策时**引用对应 ADR**（如"防腐层方案参见 ADR-012"），两者职责分离、互不重叠。

### 4.3 product 文档规范（写"做成什么 / 为什么存在"）

> product/ 放"做成什么、为什么存在、往哪走"（品牌/定位、路线图/计划、FAQ）。它回答"做成什么"，与 ADR（怎么实现）、structure（是什么样）区分。

**标准结构**：用 `assets/product-template.md`（统一骨架，正文自由）。核心是**共享头部结构**，不强求统一正文格式——slogan 可保持叙事，产品路线图可保持表格，只要都有"元信息 + 修改记录 + 与其它文档的关系"。

**文档类型差异**（正文按需组织）：

| 类型 | 正文应包含 | 举例 |
|------|-----------|------|
| 品牌/定位 | 标语、叙事、哲学依据、使用场景 | slogan |
| 路线图/计划 | 阶段、里程碑、功能列表、状态标记 | 产品路线图 |
| 决策依据 | 背景、方案、决策、后果 | **通常放 ADR，不重复进 product** |
| FAQ | 问题列表、回答、指向其它文档 | faq |

**与 ADR 的关联**：product 里的"决策依据"类内容**不放 product**——那是 ADR 的职责。product 专注"做成什么"，决策原因引用对应 ADR。

### 4.4 handoff 文档规范（会话上下文快照）

> handoff 是**会话交接文档**——记录"上一个会话做完没、下一步做什么"，让新会话快速接上。它属于 `docs/handoff/`，读写走 **`session-handoff` skill**；本 skill（travelpal-docs）**只定义分类与位置，不抢其读写职责**（接口/职责分离）。

**内容结构**（同一套，代码类与文档类各占一份）：

- **YAML frontmatter**：`task`（一句话任务）/ `status`（in-progress/done/paused）/ `date`（日期）/ `version`（可选）。
- **上一段进行到哪**：上一会话做了什么、做完没。
- **决定 / 已知坑**：关键决策、踩过的坑，供下一个会话避免重踩。
- **下一步目标**：下一个会话该做什么，按优先级。

**职责边界**：
- 本 skill（travelpal-docs）**不写** handoff 具体内容——那是 `session-handoff` 的活。
- 本 skill 只负责：handoff 属于哪类文档、放哪、什么时候标注（仍在文档生命周期三态内）。
- **不要给 handoff 建基准模板**——它的内容随会话动态变化，不需要像 ADR/design 那样固定骨架；读写流程由 `session-handoff` 定义。

### 4.5 structure 文档规范（写"某层架构是什么样"）

> structure/ 放每层架构的**静态详解**——"这一层长什么样"。每篇（如 backend/frontend/agent/data/tools/project）都是某种技术层/概念层的结构说明，与 ADR（决策）、design（规划）、product（做成什么）区分。

**标准结构**：用 `assets/structure-template.md`（不留在 docs/，收敛于此）。

**必需章节**（顺序可调）：

- **修改记录**：保留 + 动机列（每行日期/变更/动机，不删历史行）。
- **架构总览**：一段话讲清该层职责与上下层关系。
- **目录结构**：目录树带行内注释，说明每个文件职责。
- **数据流**：Mermaid 或表格描述该层数据流转。
- **维护契约**：声明「改什么必须同步什么」（如改 schema 需跑 `make gen-api`）。

**可选**：读者指南、术语表。

**与代码的关联**：structure 是"某层是什么样"的**当前快照**——代码重构引用了它，则**更新**；只是某版本快照，则**标注过时**（见「三、文档生命周期」）。不要让它变成"第二份代码"。

## 五、index.rst 导航维护

- **index.rst 是文档导航唯一事实源**（toctree 双份 = 索引漂移，禁止）。
- 增删 docs/ 文档**必须**同步 toctree——否则 Sphinx 构建报"引用不存在的文档"。
- **索引收敛到 index.rst**：ADR 编号/标题/状态表、structure 文档列表统一放 index.rst，不另设 README。

## 六、构建维护（按需）

| 动什么 | 跑什么 | 说明 |
|--------|--------|------|
| 改 docs/ 源、toctree、index.rst | `make docs` | Sphinx 构建到 docs/_build/html |
| 改后端 schema/开放接口 | `make gen-api` | 重新生成 openapi.json + 前端类型 |
| 本地预览 | `make docs-serve` | 需先 make docs，http://localhost:8001 |

**何时不该跑**：只改业务逻辑、没动 doc 源/schema/toctree 时，不用跑文档构建。
