# ADR-002: 前端架构选型

## 元信息

| 项 | 值 |
|----|----|

| 标签 | `前端架构` |
| 复审触发 | 前端页面规模增长导致组件化收益变小 / 需离线 PWA 时 |
| Supersedes | 无（原毕设 Streamlit 方案已废弃） |

## 状态

**Accepted**。

采纳 Vue 3 + Vite 前端分离架构，取代原毕设的 Streamlit 方案。原毕设 Streamlit 已废弃。

## 执行摘要

- 后端引擎（TSPTW 求解器）已构建完成，需要一个前端界面来做地图可视化、LLM Agent 对话与行程编辑。
- 在原毕设 Streamlit、FastAPI+HTMX+Jinja2+SSE、Vue 3 + Vite 三者中，选择 Vue 3 + Vite 前端分离。
- 框架内部在 Vue 3 与 React 之间选择 Vue 3：学习曲线低、高德 JS API 集成自然、体积轻、构建工具零配置。
- 核心需求由组件化清晰承载：地图可视化、Agent 对话（SSE 流式）、方案选择与行程编辑。

**Y-Statement**：在"需 2D 地图 + Agent 流式对话 + 行程编辑"的前端交互场景下，我们选择 Vue 3 + Vite 前端分离，以换取组件化清晰与生态成熟，接受"需要前端构建流程与前后端分离复杂度"。

## 背景

后端引擎已构建完成，LLM Agent 规划模块待实现，需要前端界面承载交互。核心需求：

1. 2D 地图可视化（高德 AMap JS API），展示每日行程路径。
2. LLM Agent 对话面板——自然语言交互、流式输出（SSE）。
3. 方案选择与行程编辑——选择阶段多方案对比，输入阶段可编辑，规划结果阶段只读。
4. 后期可扩展更多 Agent 交互功能。

## 决策

采纳 **Vue 3 + Vite 前端分离**：

- 组件化清晰，地图 / Agent 集成自然。
- 生态成熟，Composition API 简洁直观。
- 当前前端全部使用 Composition API 组织逻辑。

在框架内部，选择 **Vue 3 而非 React**：学习曲线低（SFC 直观、Composition API 简洁）、高德 JS API 集成自然、项目体积轻量、构建工具（Vite）零配置。

## 备选方案

### 方案 A：Streamlit（原毕设方案）

纯 Python、快速原型、无需前端知识。

**否决**：高级地图功能嵌入困难（需 iframe/组件）、Agent 实时交互不灵活、样式受限。已废弃。

### 方案 B：FastAPI + HTMX + Jinja2 + SSE

纯 Python，SSE 原生支持 stream，无构建步骤。

**否决**：复杂前端状态管理混乱、地图仍需手写 JS、两个世界拼凑感强。不推荐。

### 方案 C：React

组件化同样成熟，生态更广。

**否决**：学习曲线高（JSX + Hooks 心智负担大）、高德 JS API 需自行封装、构建工具选路迷茫。相对 Vue 3 无额外收益。

## 后果

**正面**：

- 组件化清晰，地图 / Agent 集成为自然。
- 生态成熟，后续页面可复用组件与组合式逻辑。
- 与后端 API 通过前端分离解耦，独立演进。

**负面**：

- 需要前端构建流程（Vite 构建、类型检查）。
- 前后端分离带来额外的部署与联调复杂度。

**中性**：

- 当前前端已 100% Composition API，符合现代 Vue 习惯。
- 页面规模增长后需要持续维护组件与状态分层。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 前端页面规模增长，状态管理复杂化 | 组件化收益变小、耦合增加 | 用 Pinia 集中状态 + 组合式 composable 拆分逻辑 |
| 高德 JS API 依赖 | 挂载/密钥问题导致地图白屏 | 地图组件带加载降级与错误提示 |
| 前后端类型漂移 | 接口字段不一致 | 以 OpenAPI 生成的类型作为单一来源 |

## 复审条件

- 需要离线 PWA / Service Worker 能力时，评估是否引入离线方案。
- 前端页面数量与交互复杂度显著上升，组件化收益不足时，重新审视架构。
