# ADR-003: 可视化方案变更——Cesium 3D → AMap 2D

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-07-18 |
| 标签 | `前端 / 可视化` |
| 复审触发 | 需要 3D 可视化能力 / 多源底图切换需求出现时 |
| Supersedes | 无（原 Cesium 3D 方案为毕设遗留，未成正式 ADR） |

## 状态

**Accepted**。

放弃 Cesium 3D 地球，改用高德 AMap 2D 作为路线可视化方案。

## 执行摘要

- 项目原继承毕设的 Cesium 3D 地球做可视化，但 3D 地球在旅行规划场景存在认知门槛、加载慢、坐标转换复杂、与技术栈不匹配等问题。
- 本决策完全删除 Cesium 相关代码，前端地图改用高德 JS API 2.0 重写，后端不再生成 Cesium HTML。
- 换来加载快、无坐标转换、前后端同用高德 API 的生态闭环，并减少约 500 行代码。

**Y-Statement**：在"普通用户快速看图 + 高德坐标天然一致"的旅行规划场景下，我们选择高德 AMap 2D，以换取加载快、开发效率高、技术栈统一，接受"失去 3D 可视化能力"。

## 背景

原实现继承旧毕业设计的 Cesium 3D 地球（Cesium.js 7MB+）。在旅行规划场景下存在明显问题：

- 用户认知门槛高：普通用户不习惯 3D 地球的旋转/缩放操作。
- 加载性能差：Cesium.js 体积大，拖慢首屏。
- 坐标转换复杂：高德 GCJ-02 坐标需额外转 WGS-84，有精度损失。
- 与现有技术栈不匹配：后端已全部使用高德 API（POI 搜索、驾车路径），前端用高德 JS API 可形成生态闭环。

## 决策

1. 完全删除 Cesium 3D 相关代码与配置。
2. 前端地图组件改用高德 JS API 2.0 重写（含自适应视野、信息窗体、角色图标、左右联动）。
3. 后端规划流程不再生成 Cesium HTML。
4. 清除 Cesium 相关配置项。

## 备选方案

### 方案 A：保留并优化 Cesium 3D

继续用 3D 地球，仅优化加载与坐标转换。

**否决**：用户认知门槛高、7MB+ 加载仍慢、GCJ-02 转 WGS-84 有精度损失，与后端高德生态割裂。治标不治本。

### 方案 B：Leaflet / Mapbox 等替代 2D 库

使用其他 2D 地图库。

**否决**：仍是"额外引入一套地图库 + 需处理坐标系"，不如直接复用后端已在用的高德 API，生态闭环更顺。

## 后果

**正面**：

- 加载速度提升（移除 Cesium.js，改按需加载）。
- 开发效率提升（无需坐标转换、单一坐标系）。
- 技术栈统一（前后端共用高德 API）。
- 代码量减少约 500 行（删除 Cesium 相关文件）。

**负面**：

- 失去 3D 可视化能力（旅行规划场景下不关键）。
- 原 Cesium 相关技术演示价值需通过独立 demo 保留。

**中性**：

- 地图组件保留后续可扩展位（多源底图、双层描边、轨迹动效等为预留项）。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 高德 JS API 密钥失效/加载失败 | 地图白屏无提示 | 地图组件加载降级 + 错误提示 |
| 依赖高德生态 | 换库成本高 | 地图能力收敛到单一组件，便于替换 |
| 坐标偏移（GCJ-02） | 与真实位置有偏差 | 前后端统一使用 GCJ-02，不引入二次转换 |

## 复审条件

- 出现需要 3D 可视化的需求时，再评估引入相关库。
- 需要多源底图切换（如 Mapbox/Leaflet）时，评估备选底图方案。
