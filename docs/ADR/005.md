# ADR-005: MCP 协议迁移预留

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-07-18 |
| 标签 | `MCP / 工具协议` |
| 复审触发 | 外部 AI 助手接入 / 需要独立部署工具时 |
| Supersedes | 无 |

## 状态

**Accepted**。

采用"先手写 Function Calling，工具数增长后增量迁移 MCP"的预留路线。当前 **MCP Server 角色已落地**（复用工具注册表，stdio 传输），MCP Client 角色待接入。

## 执行摘要

- 早期工具数少，手写 Function Calling 简单直接、够用。
- 当工具数增长到阈值时，增量迁移到 MCP 协议：MCP Server 暴露工具，MCP Client 替代手写调用。
- 当前工具注册表已扩展至 7 个工具，MCP Server 已实现（提供标准 `list_tools` 发现），外部 Client 尚未正式接入。
- 迁移路径：先建 Server、再换 Client、逐步迁移、最后全量切换手写 FC。

**Y-Statement**：在"工具数增长、需标准化工具互操作"的场景下，我们选择"手写 FC 起步 → 增量迁移 MCP"的预留路线，以换取标准化互操作与独立部署能力，接受"引入序列化/传输/协议层复杂度"。

## 背景

早期 Agent 工具调用采用手写 Function Calling：工具定义集中管理，调用走两阶段（先非流式检测工具调用 → 执行工具 → SSE 回传 → 流式输出）。

当工具数只有 1 个时，这套手写方案明确够用。但当工具数增长到 3-5 个乃至更多时，手动维护注册表、扩展调用链路与协议的开销会上升，因此需要一份预留的迁移路线。

## 决策

### 预留迁移路径

1. **创建 MCP Server**：包装工具注册表中的函数，通过 MCP 暴露为标准工具，支持 `list_tools` 发现。
2. **替换为 MCP Client**：聊天端点改用 MCP Client 调用，替代手写工具调用检测。
3. **逐步迁移**：新旧并存，新工具走 MCP，旧工具维持手写。
4. **全量切换**：确认所有工具经 MCP 运作后，移除手写 FC 路径。

### 当前状态

工具数已达 7 个，MCP Server 角色（复用工具注册表、stdio 传输）已实现；MCP Client 角色待接入。

## 备选方案

### 方案 A：长期维持手写 Function Calling

保持手写 FC 不变。

**否决**：工具数增长后维护与扩展成本上升，且无法与外部 AI 助手标准化互操作。

### 方案 B：一步到位切到 MCP

立即全量迁移。

**否决**：早期工具数少时 MCP 引入序列化/传输/协议层复杂度而无收益；增量迁移更稳。

## 后果

**正面**：

- 工具与外部 AI 助手标准化互操作（`list_tools` 发现）。
- 工具可独立部署、独立演进。
- 工具定义单一来源（工具注册表），手写 FC 与 MCP 复用同一套。

**负面**：

- 引入序列化/传输/协议层复杂度。
- MCP Server 暴露给外部后需考虑鉴权。

**中性**：

- 两条通道（内部 FC 流 + 外部 MCP 流）共享同一批工具函数。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| MCP Server 暴露鉴权 | 外部调用不受内部限制 | 部署时配置 API Key / 鉴权 |
| 双通道并存语义漂移 | 内外部行为不一致 | 工具定义单一来源（工具注册表） |
| 协议迁移复杂性 | 开发成本增加 | 增量迁移，先 Server 后 Client |

## 复审条件

- 需要接入外部 AI 助手（MCP Client）时，评估切换 Client 与鉴权。
- 工具数量持续增长，手写 FC 维护成本显著上升时，推进全量迁移。
