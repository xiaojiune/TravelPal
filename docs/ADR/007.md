## 状态

**Deprecated**。

当时选择 BM25 全文检索做项目文档问答；RAG 工具壳（`search_rag`）已于 **2026-08-08** 移除，BM25 检索引擎保留供未来复用。本 ADR 作为"当时决策记录"归档。

## 执行摘要

- 当时 Agent 需要回答用户关于项目自身的问题，纯靠 LLM 知识不准确，需要检索项目文档作上下文。
- 在 BM25 全文检索、ChromaDB 向量检索、直接让 LLM 回答三类中，选择 BM25：零外部依赖、项目文档量小、首次检索即生效。
- 后续实现中，该 RAG 工具壳被移除——文档问答对非技术用户无意义、技术人员直接看 GitHub；BM25 引擎保留，留待未来 raw_data 清洗后复用。

**Y-Statement**：在"回答项目自身问题需精确引用文档"的场景下，我们曾选择 BM25 全文检索，以换取零依赖与即时生效，接受"无语义理解"。该决策现已因应用场景变化而暂停（工具壳移除、引擎保留）。

## 背景

Agent 在对话中需回答用户关于项目自身的问题（功能、技术栈、架构等）。纯靠 LLM 自身知识难以保证准确性与及时性，需要检索项目文档作为知识上下文。

## 决策

选择 BM25 全文检索：中文用 jieba 分词 + 停用词过滤，按文档标题切块，检索注入 system prompt；低分时自动过滤单字重检。理由：项目文档体量小，BM25 精确匹配足够；零外部依赖；首次构建即生效；未来可叠加向量检索（接口不变）。

## 备选方案

### 方案 A：BM25 全文检索（当时采纳）

零外部依赖、首次检索即生效、项目文档量小够用。

**否决**：无语义理解（同义词/近义词不匹配）——但当时文档量小，可接受。

### 方案 B：ChromaDB 向量检索

语义匹配强，自动处理同义词。

**否决**：需 embedding API 或本地模型（首次构建慢），依赖重（约 50MB+）。

### 方案 C：直接让 LLM 回答

最省事。

**否决**：知识更新不及时、prompt 长度有限、无法精确引用。

## 后果

**正面**（当时）：

- 精确引用项目文档，回答与代码一致。
- 零外部依赖，小体量下 BM25 足够。

**负面**（导致迁移）：

- 文档问答对非技术用户意义有限；技术用户直接看 GitHub 更高效。
- BM25 无语义匹配，检索质量受分词影响。

**中性**：

- BM25 检索引擎保留，供未来 raw_data 清洗后复用。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 检索质量受分词影响 | 命中不准 | jieba 分词 + 停用词 + 低分重试 |
| 语义缺失 | 同义词不匹配 | 未来可叠加向量检索引擎（接口不变） |

## 复审条件

- 需要为"非技术用户"提供项目文档问答、且 raw_data 清洗完成时，重新评估启用 RAG。
