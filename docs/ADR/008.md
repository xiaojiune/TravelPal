## 状态

**✅ 已采纳**。

## 背景

项目已进入稳定期，核心 CA/VNS 引擎与全栈链路稳定。为应对后续功能扩展（多 Agent、异步任务、外部服务集成），需要一份架构演进路线图，明确**哪些框架引入、哪些不引入、引入顺序如何**，避免盲目堆砌框架。

## 核心决策

### 1. MCP：接入，但先做 Server 角色

MCP 官方 SDK 原生支持对称角色，一个实例可同时作为 client + server：

- **Server 角色**：把 `poi_lookup` / `get_plan` / `search_rag` 暴露给 LLM 调用，确定性收益，优先做。**需配置 API key 鉴权**——Server 角色暴露给外部 LLM 后不再受内部调用限制，必须校验调用方身份（与现有 Agent 内部调用走不同路径）。
- **Client 角色**：连接外部 MCP 服务（天气/酒店/交通）。当前外部 MCP 生态不成熟，多数服务仍是普通 HTTP API——**只有 HTTP API 就直接 httpx 调，别为 MCP 而 MCP**。等找到真实可用的外部 MCP 服务再接。

**部署形态：独立服务 + 原生懒加载**。MCP Server 作为独立进程运行（`python -m backend.mcp.server`），不内嵌于任何 Skill；opencode 通过 `experimental.mcp_lazy_load: true` 实现按需启动，工具不再常驻占用上下文。

**职责边界：只复用叶子工具，不引用编排层**。MCP Server 遍历 `TOOL_REGISTRY` 注册叶子工具（如 `poi_lookup` / `search_rag`），**永不引用 LangChain 编排层**——内部流（LangChain 编排）服务项目自身的 Agent 对话，外部流（MCP）服务外部 AI 助手，两条通道共享同一批工具函数，单一事实来源。外部 AI 助手通过 MCP `list_tools` 自行判断何时调用；可用 Skill 作**触发引导**（仅提示"何时适合用这些工具"，不含 mcp.json，不参与执行，可选用）。

> 本地 stdio 传输时进程边界即鉴权；远程部署时仍需 API key 鉴权（见下）。

#### 实践示例：WeatherService 防腐层

以天气服务为例，体现"接口先行、实现可插拔"：

```
backend/domain/WeatherService.py              # Protocol: async get_weather(city) -> WeatherInfo
backend/infrastructure/http_weather_service.py  # 当前实现，用 httpx 调普通 HTTP API
backend/infrastructure/mcp_weather_service.py   # 未来实现，连接外部 MCP 服务
```

**接口先行**：今天 HTTP 实现跑通，明天 MCP 实现替换**零改动**。判断标准同上——天气服务若仍是普通 HTTP API，就直接 httpx 调，不引入 MCP；等真实可用外部 MCP 服务出现，再补 `mcp_weather_service.py`。

> 注意：接口粒度要通用（`get_weather(city)`），避免两个实现互相迁就。

### 2. Alembic：接入数据库迁移

当前仅 1 张表（`HistoryRecord`），但 ADR-008 规划的 `plan_tasks` 等会让 schema 增长。**单表时接入成本最低**，先行铺路：

- `poetry add --group dev alembic`
- `alembic init -t async backend/data/migrations`（async 模板，匹配 async SQLAlchemy）
- `env.py` 配置 `target_metadata = Base.metadata`
- Makefile 的 `dc-migration` 占位替换为真实命令（`alembic revision --autogenerate` / `alembic upgrade head`）

优先级：**Alembic（低风险高确定性）> WeatherService**，两者都在 LLMService 防腐层（轴 1）之后推进。

### 3. LangChain：引入，但用防腐层包住

目标目录结构（DDD 风格）：

```
backend/
├── domain/                    # 领域层（防腐层接口）
│   └── LLMService.py          # Protocol: async stream() / complete()
├── infrastructure/
│   ├── llm/
│   │   ├── langchain_impl.py  # 用 LangChain ChatOpenAI 实现 LLMService
│   │   ├── dspy_optimizer.py  # 占位，不实现
│   │   └── factory.py         # 实现切换
│   └── retrieval/
│       ├── llama_index_retriever.py  # 占位，不实现
│       └── hybrid_retriever.py       # 占位，不实现
```

第一轴只做 `domain/LLMService` 防腐层（Protocol 定义 `async stream()` / `complete()`）+ `infrastructure/llm/langchain_impl.py`。`chat.py` 只依赖 `LLMService` 接口，`factory` 切换实现。`engine/` 和 `api/` 不动。

> **现状错位**：`backend/agent/` 目录混了 3 类东西——`chat.py`（编排）、`tools/poi.py`（直接调 openai）、`rag.py`（BM25 检索）。防腐层正是为理清这团耦合而生。

### 4. Django：不引入

Django 适合大量关系模型 + 后台 CRUD 场景。当前系统无此需求，引入是过度设计。若未来出现真正的多用户系统，再评估整体替换或 FastAPI + auth 中间件方案。

### 5. Celery：先任务表，后平滑迁移

- **落地形态（2026-08-04 已完成）**：直接采用 Celery（broker=redis），`plan_tasks` 表（`id/task_type/status/request_params/result/error/created_at/started_at/finished_at`），结果由**任务内自写 plan_tasks 表**（复用现有 async SQLAlchemy，不配 Celery result backend）。`POST /api/suggest` / `POST /api/plan` 改为提交任务 → 返回 `task_id`，前端轮询 `GET /api/tasks/{id}`。
  > 前提：依赖**单 uvicorn worker**（当前部署正是单 worker）。若将来改为多 worker，进程内后台线程无法跨进程共享任务状态，此时即是迁移多 Celery worker 的信号。
- **保留演进**：多 worker 扩展时仅需水平扩容 celery worker（docker-compose `worker` 服务已就位），**前端轮询接口不变**，保证切换时前端零改动。

### 6. 观测性：轻度接入

只做**业务指标**（token 消耗 / 调用次数 / API 耗时），用 `prometheus_client` 的 Counter / Histogram + `/metrics` 端点。**不部署 Grafana**（服务器内存紧张），**不做系统指标**（CPU/内存）。**`/metrics` 需限制访问**——前端有 Nginx 前置，应仅允许内网或加 Basic Auth，避免公网泄露调用数据。

### 7. 组件化理念

只引用框架特定功能：prompt 用 DSPy、编排用 LangGraph、RAG 用 LlamaIndex。框架是手段不是目的，用防腐层 + 依赖倒置解耦。

> 反方观点：每引一个框架就多一层防腐翻译逻辑。应**按需渐进**，一次只动一个轴，别一次全上。

### 8. 换框架纪律

- 每引入框架前先写单元测试锁定现有行为，再替换实现——**测试是防腐层是否有效的试金石**。
- 别把换框架和改业务混一起，一次只动一个轴。

### 9. 演进式架构：单 Agent 中央编排

**决策**：当前及可预见阶段采用**单 Agent 中央编排**（Router-Executor Pattern），不引入多 Agent。

**模式本质**：一个 LLM 大脑（Router）通过 Function Calling / MCP 选择并调用多个执行器（Executor）。路由由 LLM 自动完成（看工具 schema 决定调哪个），代码只做"检测 tool_call → 分发执行"。

```
大脑（Router）        手（Executor）
   LLM 决策             TOOL_REGISTRY 叶子工具
     │                      ├─ poi_lookup    （category: poi）
     ├─ 选工具 ────────────→ ├─ search_rag    （category: rag）
     └─ 回填结果            └─ 未来: get_plan （category: planning）
```

**演进式策略**：**按多 Agent 设计，按单 Agent 执行**。
- 每个"活 Agent"是独立职责边界 + 独立入口（chatAgent = `chat.py`，PlanAgent = `planner.py`），共享同一套 LLMService + TOOL_REGISTRY
- **不提前引入**主管 Agent（单核时编排层即主管）、Agent 通信协议（单核时 LLM 上下文即介质）、LangGraph 状态机（属编排层，轴 1 防腐层之后才需要）
- 工具是需求的产物不是架构的装饰：现有 2 个工具（poi/rag）跑通范式，真实需求出现时再按 category 扩展

**工具分组（category）**：在工具数量少时即确定分类维度，为将来 MCP 分组、工具 schema 组织、前端展示提供依据：

```
TOOL_REGISTRY = {
    "poi_lookup": {"fn": ..., "category": "poi"},
    "search_rag": {"fn": ..., "category": "rag"},
    # 未来: "get_plan" → planning, "ocr_parse" → vision
}
```

**与轴 4 的衔接**：PlanAgent 激活依赖异步任务表——路径计算（VNS）分钟级耗时，对话式触发需异步任务（轴 4）+ 远期 LangChain 编排层组合支撑。

## 落地顺序

| 顺序 | 轴 | 内容 | 依赖 | 回滚方式 |
|------|-----|------|------|---------|
| 1 | domain/LLMService 防腐层 | Protocol + factory，不依赖新框架 | 无 | 还原 chat.py 依赖，删 domain/ |
| 2 | Alembic 数据库迁移 | 单表时低成本接入，铺路 plan_tasks | 无 | `alembic downgrade` 回退 schema |
| 3 | MCP Server | 暴露现有工具给 LLM | 轴 1 | 关闭鉴权入口，删除暴露层 |
| 4 | 异步任务表 | plan_tasks + 轮询 | 轴 2 | 还原 /api/plan 同步执行（已完成：Celery + plan_tasks，suggest/plan 提交任务返回 task_id，前端轮询） |
| 5 | 观测性埋点 | 业务指标 + /metrics | 无 | 删 /metrics 端点，移除埋点 |
| 6 | MCP Client | 接入真实外部 MCP。当前已落地 WeatherService 防腐层接口规范 + factory（HTTP 基线、配置级降级），HTTP/MCP 实现均为 TODO 占位 | 轴 3 | 切回 httpx 实现，接口不变 |
| 7 | DSPy / LlamaIndex / CrewAI | 按需组件化 | 轴 1 | 防腐层内切换回原实现 |
