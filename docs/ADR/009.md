# ADR-009: 前端组件库引入策略——Naive UI 分步替换

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-08-01 |
| 标签 | `前端 / 组件库` |
| 复审触发 | 组件库生态变化 / 组件 API 不满足需求时 |
| Supersedes | 无 |

## 状态

**Accepted**。

引入 Naive UI 但**分步替换、不全量重构**：先迁收益最大的表单/列表页，其余观察；同时落地品牌色板与 Agent-driven UI 地基。

## 执行摘要

- 前端原为手写 CSS，无组件库；五页（Home/Suggest/Plan/Agent/History）中表单校验、分页、弹窗等重复造轮子成本上升。
- 选择引入 Naive UI（Vue 3 原生 TS 组件库），但**分步迁移**而非全量替换——全量会丢失定制风格与自定义交互，且 diff 巨大、回归风险高。
- 真正受益点是 HomePage 表单（校验/输入体验）与 HistoryPage 列表（分页/空态/删除确认）。
- 落地前置：中文 locale（`config-provider` + `zhCN`）与按需引入（`unplugin-vue-components` + `NaiveUiResolver`）。
- 同步落地品牌色板（theme.ts 单一来源）与 Agent-driven UI 地基（JSON Schema 驱动路线 A）。

**Y-Statement**：在"五页组件复用、需控制迁移风险"的场景下，我们选择 Naive UI 分步替换，以换取表单/列表体验与统一组件，接受"保留手写定制风格、分步迁移的改造复杂度"。

## 背景

前端当前为手写 CSS 的 Vue 3 + TypeScript，无组件库。随着页面增多（Home/Suggest/Plan/Agent/History），表单校验、列表分页、弹窗等基础组件重复造轮子成本上升。

## 决策

### 引入，但分步替换，不全量重构

全量替换代价：丢失现有定制风格（地图/行程联动、SSE 打字机交互均为手写）；巨大 diff、回归风险高；破坏自定义交互（地图、行程表、Agent 打字机）。真正受益的只有表单页与列表页。

### 迁移范围界定

| 页面 | 迁移 | 理由 |
|------|------|------|
| HomePage | 首批 | 表单控件收益最大 |
| HistoryPage | 首批 | 列表/分页/弹窗收益大 |
| SuggestPage | 观察 | 卡片布局偏定制 |
| PlanPage | 观察 | 依赖地图/行程联动 |
| AgentPage | 观察 | 依赖 SSE 打字机 |

### 迁移纪律

一次只迁一个页面，跑通再迁下一个；迁移后 lint / vue-tsc / 功能自测通过；不追求全量替换，首批收益确认后再评估。

### 实现前置

- **中文 locale**：必须用 `config-provider` + `zhCN` 包裹，否则日期/分页/空态文案为英文。
- **按需引入**：全量 import 会让构建体积暴涨，在构建配置中用 `unplugin-vue-components` + `NaiveUiResolver` 按需注册。

### 品牌色板（theme.ts 单一来源）

引入前全站色值为散落硬编码。做法：以 theme.ts 作为唯一事实来源，生成 `themeOverrides` 供组件库、`applyThemeVars()` 写 `--tp-*` CSS 变量；语义色统一；地图路线功能色板独立保留。

### Agent-driven UI 地基（JSON Schema 驱动路线 A）

随演进式架构，前端需支持"AI 在对话中弹出效率工具"（表单卡片 / 结果卡片）。采用 JSON Schema 驱动：工具 schema 单一来源自动渲染，新工具零前端改动；渲染器用自写轻量组件（依赖 Naive UI 控件按 schema 类型分发），不引入 JSON Forms 等大框架。

## 备选方案

### 方案 A：Naive UI 分步替换（采纳）

Vue 3 原生 TS、组件 API 现代、按需引入可控体积。

**否决**：无——采纳本方案。

### 方案 B：全量重构一次替换

一次把所有页面迁到 Naive UI。

**否决**：丢失定制风格与自定义交互、diff 巨大、回归风险高。

### 方案 C：继续手写 CSS / 引入其他库

不使用组件库，或改用 Element Plus / Ant Design Vue。

**否决**：手写重复造轮子成本高；Element/Ant 生态虽广但 TS 支持与组件 API 不如 Naive 现代。

## 后果

**正面**：

- 表单/列表等基础组件复用，体验统一。
- 品牌色板单一来源，换品牌主色只动 theme.ts。
- Agent-driven UI 地基为后续"AI 弹窗工具"铺路。

**负面**：

- 分步迁移改造周期长。
- 手写定制风格与 Naive 主题 token 需对齐（品牌色视觉统一成本）。

**中性**：

- 地图/行程/打字机等自定义交互保留手写，只迁移通用控件。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 全量 import 使构建膨胀 | 构建体积上升 | 按需引入（NaiveUiResolver） |
| 中文文案缺失 | 组件文案英文 | config-provider + zhCN 包裹 |
| 迁移破坏定制风格 | 交互回归 | 一次一页、跑通再迁、lint/vue-tsc 自测 |

## 复审条件

- 组件库生态变化或组件 API 不满足需求时，评估是否替换。
- Agent-driven UI 接入实际业务工具（get_plan/add_poi 表单卡片）后，评估 SchemaFormCard 是否扩大覆盖。
