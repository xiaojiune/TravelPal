# ADR-009: LLM 编排层选型——LangGraph 维持，PydanticAI 不引入

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-08-08 |
| 标签 | `LLM 编排 / 选型` |
| 复审触发 | 需要图级多 Agent 编排之外的强结构化输出兜底时 |
| Supersedes | 无 |

## 状态

**Accepted**。

编排层维持 LangGraph，不引入 PydanticAI；PydanticAI 提出的"结构化输出 + 校验 + 失败重试"能力通过防腐层自建 helper 吸收（符合自写优先原则）。

## 执行摘要

- 在"LangGraph vs PydanticAI"的编排层选型中，选择维持 LangGraph。
- 理由：我们的编排是 Router-Executor 循环（LLM 决策 → 工具执行 → 回填 → 再决策），LangGraph 条件边 + 自环是原生表达；PydanticAI 控制流偏弱、多 Agent 演进路径锁死、与防腐层抢边界、成熟度低。
- 但 PydanticAI 暴露了一个真实缺口：**"LLM 输出不可信，需结构化 + 校验 + 失败重试"**。拆成两个场景吸收：文本→模型的结构化解析（自建 helper）、工具参数容错 + 失败重试（已实施，工具调用包 try/except 回填错误让 LLM 自纠）。

**Y-Statement**：在"需图级编排 + 结构化输出兜底"的场景下，我们选择维持 LangGraph 并自建结构化/容错能力，以换取控制流清晰与演进空间，接受"部分能力需自写"。

## 背景

用户提出"LangGraph vs PydanticAI，编排层选型是否要换"。PydanticAI 是 Pydantic 团队推出的轻量 Agent 框架，以结构化输出为卖点（自动解析/校验/失败重试 re-prompt）。需评估是否替换现有 LangGraph 编排层，或将其能力吸收进项目。

## 决策

1. **编排层维持 LangGraph**：Router-Executor 与多 Agent 演进路径均正确，无替换动机。
2. **不引入 PydanticAI 框架**：控制流弱、演进锁死、边界冲突、成熟度低，四维度均不支持。
3. **自建"LLM 输出结构化 + 容错"能力**（两场景）：场景二已实施；场景一（结构化解析 helper）列为待实施项。

### 两场景吸收

- **场景一：文本 → 模型（结构化解析）**。LLM 调用返回原始文本，结构化解析分散在调用方。正确做法：在防腐层自建轻量结构化解析 helper（传目标模型 + LLM 输出，自动解析/校验/失败重试 re-prompt），收敛为单一实现。
- **场景二：工具参数容错 + 失败重试**。LLM 误调工具（参数缺失/类型错误）时，编排层不中断整轮对话，而是回填错误让 LLM 看到后自我修正重调。已实施：工具执行包 try/except，异常转 `{"error": ...}` 回填 tool 消息（PydanticAI re-prompt 重试的手写等价实现）。

## 备选方案

### 方案 A：切换 PydanticAI 作为编排层

用 PydanticAI 完全替换 LangGraph。

**否决**：控制流弱（偏线性 tool-call 循环，难表达条件边自环）、多 Agent 演进锁死、与防腐层抢边界、0.x 成熟度低 API 不稳。

### 方案 B：维持 LangGraph + 自建结构化/容错能力（采纳）

保留现状零重构，吸收 PydanticAI 最核心能力。

**否决**：无——采纳本方案。

## 后果

**正面**：

- 控制流清晰，多 Agent 演进路径保留。
- 结构化输出与工具容错能力落地，LLM 输出不可信问题得到兜底。

**负面**：

- 结构化解析 helper 需自建（待实施），前期有工作量。

**中性**：

- 换框架的讨论沉淀为"吸收能力而非换框架"的结论。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 结构化解析分散 | 各调用方手写解析易漂移 | 收敛到防腐层单一 helper |
| 工具误调中断整轮 | 对话体验受损 | try/except 回填 error 让 LLM 自纠 |
| LangGraph 停更 | 编排层失效 | 状态转移层与框架解耦，替换成本限 Adapter |

## 复审条件

- 出现需要"图级多 Agent 编排之外的强结构化输出兜底"时，再评估是否需要专用框架。
