## 背景

前端当前为手写 CSS 的 Vue 3 + TypeScript，无组件库。随着页面增多（Home / Suggest / Plan / Agent / History 五页），表单校验、列表分页、弹窗等基础组件重复造轮子的成本上升，考虑引入 Naive UI（Vue 3 原生 TS 组件库）。

## 核心决策

### 1. 引入，但分步替换，不全量重构

全量替换的代价：

- 丢失现有定制风格（地图/行程联动、SSE 打字机交互均为手写）
- 巨大 diff，回归风险高
- 破坏自定义交互（AmapMap 地图、SchedulePanel 行程表、AgentPage 打字机）

**真正受益的只有两处**：HomePage 表单（表单校验/输入体验）+ HistoryPage 列表（分页/空态/删除确认）。

### 2. 迁移范围界定

| 页面 | 迁移 | 理由 |
|------|------|------|
| HomePage | ✅ 首批 | 表单控件收益最大 |
| HistoryPage | ✅ 首批 | 列表/分页/弹窗收益大 |
| SuggestPage | ⏸ 观察 | 卡片布局偏定制 |
| PlanPage | ⏸ 观察 | 依赖地图/行程联动 |
| AgentPage | ⏸ 观察 | 依赖 SSE 打字机 |

### 3. 迁移纪律

- 一次只迁一个页面，跑通再迁下一个
- 迁移后前端 lint / vue-tsc / 功能自测必须通过
- 不追求全量替换，两个首批页面收益确认后再评估剩余页面

### 4. 实现前置（两个必踩的坑）

- **中文 locale**：naive-ui 默认英文，必须用 `config-provider` + `zhCN` 包裹应用，否则日期/分页/空态文案是英文。
- **按需引入**：全量 import naive-ui 会让构建体积暴涨，需在 `vite.config.js` 配置 `unplugin-vue-components` + `NaiveUIResolver` 实现按需注册。

> 可选：迁移后手写 CSS 与 naive-ui 主题 token 共存，需对齐品牌色（primary 色值）保持视觉统一。

### 5. Agent-driven UI 展示（承接 ADR-008 §9）

随演进式架构（单 Agent 中央编排）推进，前端需支持"AI 在对话中弹出效率工具"。两类可弹出组件：

- **表单卡片（Form Card）**：AI 需要用户补充参数时弹出输入表单
- **结果卡片（Result Card）**：工具执行结果的结构化展示（现有 `pendingPois` 待选栏即雏形）

**两条路线对比**：

| | A：JSON Schema 驱动 | B：硬编码组件映射 |
|---|---|---|
| 表单来源 | 工具 schema 单一来源自动渲染 | 每个工具手写 Vue 组件 |
| 通用性 | 新工具零前端改动 | 每加工具都要写组件 |
| 复杂度 | 需自写渲染器 | 现状简单 |

**决策：采用路线 A**（JSON Schema 驱动）。

**关键技术点**：
1. **schema 单一来源改造**——内部流 `TOOL_DEFINITIONS` 从手写改为从函数类型注解自动生成，与 MCP `input_schema` 同源（MCP 已自动生成），一处定义多处消费
2. **渲染器选 A1 自写轻量组件**——依赖 Naive UI 的 `n-input` / `n-input-number` / `n-select` 按 schema 类型分发渲染（约 100 行），契合本 ADR 的组件库策略，**不引入 JSON Forms 等大框架**

**时序**（与 Naive UI 迁移协同）：
- 阶段 1：Naive UI 迁移（HomePage / HistoryPage）——本 ADR §1-4
- 阶段 2：Agent-driven UI 地基——schema 单一来源 + 泛化 `pendingPois` 为通用 tool_result 卡片渲染器 + schema→表单轻量组件
- 阶段 3：引入 `get_plan` 时表单卡片自然启用
