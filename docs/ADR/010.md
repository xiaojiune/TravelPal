# ADR-010: 认证/鉴权通道选型——httpOnly Cookie + Redis 会话，JWT 不引入

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-08-27 |
| 标签 | 认证 / 选型 |
| 复审触发 | 出现无状态水平扩展 / 移动端 / 第三方或微服务间鉴权需求时 |
| Supersedes | 无 |

## 状态

**Accepted**。

## 执行摘要

- 在「Cookie + Session vs JWT」的认证通道选型中，选择 **httpOnly Cookie + Redis 服务端 Session**。
- 理由：EventSource（SSE）无法自定义 Authorization header，Cookie 自动携带天然兼容流式；服务端可撤销（登出即删）；单机 + 已有 Redis 成本低；httpOnly 防 XSS 取 token。
- 代价：需 CSRF 防护、CORS credentials、Cookie 跨域配置；无状态水平扩展需后续迁移。

**Y-Statement**：在「浏览器单机 SPA + SSE 流式 + 已有 Redis」的上下文下，我们选择 httpOnly Cookie + Redis 服务端会话，以换取 SSE 兼容与可撤销登出，接受「需 CSRF/CORS 跨域处理、无状态扩展受限」。

## 背景

用户系统引入前，history_records 用 device_id 软鉴权，无真实账号体系。现需为「注册/登录 + 数据归属 + Admin 操作台」搭建认证。前端是前后端分离的 Vue3 SPA，/api/chat 用 SSE 流式，后端单机 + 已有 Redis。需在 Cookie+Session 与 JWT 间定鉴权模型。

## 决策

1. **浏览器用 httpOnly Cookie + Redis 服务端 Session**：登录后服务端创建会话存 Redis，Set-Cookie（httpOnly + Secure + SameSite）；登出删会话即撤销。
2. **密码哈希 + SECRET_KEY 走 env**：密码用 bcrypt/argon2 哈希；SECRET_KEY 只放 .env，不进 git。
3. **CSRF 防护**：SameSite=Strict/Lax + CSRF token；CORS 严格配置 credentials。
4. **第三方/外部 AI 助手（MCP Client）走 API Key / Bearer 双轨**：与浏览器 Cookie 不同通道（MCP Server 暴露本就需鉴权）。
5. **不引入 JWT 作为主鉴权**：仅在复审条件触发时评估。

## 备选方案

### 方案 A：无状态 JWT（Bearer）

无状态签名 token，Authorization header 携带。

**否决**：EventSource 无法自定义 header，SSE/流式兼容差需绕行；token 不可撤销（登出难、泄露难召回）；刷新/续期需自行管理；当前单机无状态扩展需求。

### 方案 B：Cookie + JWT 并存（混合）

同时支持 Cookie 会话与 JWT Bearer 两种凭据。

**否决**：两套鉴权并存增加复杂度与攻击面，当前无必须双凭据的业务场景，违背"一次只动一个轴"。

## 后果

**正面**：

- SSE/EventSource 自动带 cookie，流式接口无需处理 Authorization header。
- 服务端会话可撤销（登出即删）、可多端管理、httpOnly 防 XSS 取 token。
- 单机 + 已有 Redis，成本低、实现简单。

**负面**：

- 需 CSRF 防护（SameSite + token）、CORS credentials、跨域 Cookie 配置。
- 服务端有状态，无状态水平扩展需后续迁移到 JWT（或共享会话存储）。
- 移动端/原生客户端拿不到 Cookie 场景不友好（届时触发复审）。

**中性**：

- Cookie/JWT 之争沉淀为「按触发条件切换」而非"哪套更好"。
- 与实时通道选型（ADR-011）解耦，可各自独立演进。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| CSRF | 盗用登录态执行非预期操作 | SameSite=Strict/Lax + CSRF token |
| Cookie 跨域配置错误 | 前端请求不带/带错凭据 | CORS 受控 credentials + 明确 Origin 白名单 |
| 登录爆破 | 撞库/暴力破解 | 登录限流 + 失败计数 + 验证码兜底 |
| 越权（他人数据） | 用户操作到他人记录 | 归属校验（user_id）+ RBAC（role=admin） |
| SECRET_KEY 泄露 | 会话伪造 | 只放 .env 不进 git + 定期轮换 |

## 复审条件

- 出现**无状态水平扩展**（多实例共享会话困难）、**移动端/原生客户端**（Cookie 不友好）、**第三方/微服务间鉴权**（需 Authorization header）时，重新评估 JWT。
