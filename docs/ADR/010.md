## 状态

**✅ 已采纳**——作为技术债基线清单，配合 ADR-008 落地顺序渐进清理。

## 背景

轴 1~6 落地后，后端形成 `api → agent/tools + engine + domain/infrastructure → data/model → celery` 的完整分层。本 ADR 记录一次全面架构评估：**方向正确处**与**真实隐忧**并存，隐忧按严重度排序，供后续演进决策参考。

## 总体评估

结构经过认真设计，方向正确，尤其在「依赖倒置 + 防腐层 + 双流复用」上扎实。但存在几处真实隐忧，不应因当前系统可用而忽视。

### 做对的地方

1. **依赖方向正确**：`domain/` 零依赖纯接口 → `infrastructure/` 只依赖 domain → `mcp/` 是旁路出口（消费上层工具）。依赖方向定型后，换框架的爆炸半径很小。
2. **防腐层是真防腐**：LLMService / WeatherService 只留接口 + factory 配置驱动，HTTP/MCP 实现可插拔。坚持「接口先行、实现 TODO 占位」是多数人做不到的克制。
3. **TOOL_REGISTRY 单一事实来源**：内部 FC 流 + 外部 MCP 流复用同一批叶子工具，避免「两套工具两套实现」的经典腐化。
4. **异步化踩对痛处**：40s 驾车 API 是真正瓶颈，Celery + plan_tasks 自写表把同步阻塞变成轮询，且预留了平滑迁移的口子。

## 技术债清单

### 1. `agent/` 包职责混杂（中）

`chat.py`（编排）+ `tools/`（叶子工具）+ `planner.py`（@placeholder 未接线）+ `commentator.py` 挤在一个包。现在靠 ADR-008 §9「演进式架构」兜底，但**真正切 LangChain 编排时这层要重划边界**，成本不会小。`planner.py` 是明确的未接线代码，一直挂着。

> 处置：配合 LangChain 编排层接入（ADR-008 轴 7）时重划——编排层独立，叶子工具留 tools/，planner 激活或清理。

### 2. `domain/` 覆盖不全（中）

只有 LLMService 和 WeatherService 两个 Protocol。行程 / 景点 / 任务这些**业务领域对象**仍以 dict 形态散在 engine/api/celery 之间，类型弱、无契约。防腐层只保护了「换 LLM/天气」两个点，保护不了「换编排/换存储」。当前 domain 是**战术防腐**而非**战略领域层**。

> 处置：按需渐进，随业务对象稳定后再提纯为协议类型。

### 3. `celery_app.py` 是隐式 hub（中）

建表 + 发任务 + 执行引擎 + 解决 asyncpg 跨 loop，又被 routes.py 和 tools/plan.py 同时依赖。循环导入靠延迟 import 压住，但**职责过重的单模块是未来重构最痛的起点**。

> 处置：观察，若任务类型增加（suggest/plan/其他），拆出任务分发注册表。

### 4. Numba 内核重复（低，零风险）

ca.py 与 vns.py 各保留一份逐字符相同的 `_cal_fitness_numba`。这是明确技术债——**改一处忘另一处是真实风险**，非风格问题。

> 处置：提取共享内核到 `backend/engine/fitness.py`，两求解器 import 复用。改动小、可立即执行。

### 5. 配置管理原始（低）

`backend/config.py` 全是 `os.getenv` 裸读，无集中校验、无类型。配置项已增至 AMAP/LLM/CELERY/WEATHER/SKIP_DB 多组，裸读难维护。

> 处置：迁移 `pydantic-settings`，集中管理默认值 + 类型 + 校验。

### 6. 契约测试缺失（持续）

engine 层 42 个测试扎实，但 api/celery/mcp 层零自动化测试，端到端全靠手动脚本。防腐层（domain/LLMService）的**核心价值恰恰需要契约测试锁定**——「换实现行为不变」没有测试验证就是空话。

> 处置：新引入框架或改防腐层实现前，先补契约测试（ADR-008 §8 换框架纪律的落地前提）。

### 7. 任务无重试机制（低）

`task_acks_late=True` 但无 autoretry。驾车 API 偶发失败直接 `failed`，用户只能重新提交——错峰重试缺失。

> 处置：任务失败重入 broker 或标记 retryable，按需实现。

### 8. 类型三处手工同步（中）

`backend/typedefs.py`（后端内部）+ `frontend/src/types.ts`（前端）+ `docs/structure/data.md`（文档）描述同一批 PlanResult 结构，全靠手工对齐，漂移风险真实存在。

> 处置：中长期以 OpenAPI 生成 / 单一 schema 源驱动，手工同步为过渡态。

### 9. 驾车 API 无后端缓存（低）

同城市同景点的 cost_matrix 每次全量拉 40s，除前端 store 显式复用外无后端缓存层（opentime2 哈希缓存此前判定暂不做）。

> 处置：高德结果按 (city, 景点集) 缓存到 Redis，独立于轴 4 的并行拉取策略。

### 10. API 无版本化（观察项）

全部挂 `/api/` 无 `/api/v1` 前缀。单服务自用、无外部消费者，**当前可接受**；若开放对外或出现破坏性变更需求再引入。

## 处理优先级

| 优先级 | 项 | 理由 |
|--------|-----|------|
| P0（立即） | Numba 内核去重（#4） | 小改动、零风险、消除改一忘一隐患 |
| P0（立即） | config 迁移 pydantic-settings（#5） | 小改动、提升配置可维护性 |
| P1（配合轴 7） | agent 包边界重划（#1） | 依赖 LangChain 编排层接入时机 |
| P1（持续） | 契约测试补 api/celery/mcp 层（#6） | 换框架纪律的前提，随改动补 |
| P2（按需） | domain 覆盖业务对象（#2）/ celery hub 拆分（#3）/ 任务重试（#7）/ 类型单一来源（#8）/ API 缓存（#9） | 随业务增长自然触发 |
| 观察 | API 版本化（#10） | 无外部消费者前不动作 |
