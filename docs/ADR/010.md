## 状态

**✅ 已采纳**——作为技术债基线清单，配合 ADR-008 落地顺序渐进清理。

## 背景

ADR-008 轴 1~7 全部落地后，后端形成 `api → agent(orchestrator + tools) + engine + domain/infrastructure → data/model → celery` 的完整分层，并叠加观测性与 MCP 旁路出口。本 ADR 于轴 1~6 时首次评估，现于全部轴落地后重新审视：记录**已消解项**与**剩余隐忧**，按严重度排序。

## 总体评估

结构经过认真设计，方向正确。轴 1~7 落地后，分层完整、依赖方向清晰，主要隐忧集中在「清理性技术债」（dead code、重复代码）而非「结构性缺陷」。

### 做对的地方

1. **依赖方向正确**：`domain/` 零依赖纯接口 → `infrastructure/` 只依赖 domain → `mcp/` 是旁路出口（消费上层工具）。依赖方向定型后，换框架的爆炸半径很小。
2. **防腐层是真防腐**：LLMService / WeatherService 只留接口 + factory 配置驱动，HTTP/MCP 实现可插拔。坚持「接口先行、实现 TODO 占位」是多数人做不到的克制。
3. **TOOL_REGISTRY 单一事实来源**：内部 FC 流 + 外部 MCP 流复用同一批叶子工具，避免「两套工具两套实现」的经典腐化。
4. **异步化踩对痛处**：40s 驾车 API 是真正瓶颈，Celery + plan_tasks 自写表把同步阻塞变成轮询，且预留了平滑迁移的口子。
5. **LangGraph 编排收敛（本次修订新增）**：编排职责从 api 层移入 `orchestrator.py`（ADR-008 §9 单 Agent 中央编排落地），chat 端点只剩 SSE 组装；只引 `langgraph`（含 langchain-core）不引 langchain 主包，LLM 调用仍走防腐层。
6. **观测性落底（本次修订新增）**：轴 5 prometheus_client 多进程聚合，`/api/metrics` 三进程（backend/worker/MCP）数据归一，Nginx Basic Auth 兜底访问控制。
7. **组件化克制**：轴 7 对 DSPy/LlamaIndex 只建占位不实现，CrewAI 直接舍去（多 Agent 用 LangGraph 多图编排，两套编排框架并存是架构腐化）。

### 本次修订消解项

- **#1 agent 包职责混杂（原）**：编排已独立为 `orchestrator.py`，主要矛盾消解；剩余清理归入 #3/#4（见下）。
- **观测性**：原「未实现」状态已落地。

## 技术债清单

### 1. Numba 内核重复（低，零风险）

ca.py 与 vns.py 各保留一份逐字符相同的 `_cal_fitness_numba`。这是明确技术债——**改一处忘另一处是真实风险**，非风格问题。

> 处置：提取共享内核到 `backend/engine/fitness.py`，两求解器 import 复用。改动小、可立即执行。

### 2. 配置管理原始（低）

`backend/config.py` 全是 `os.getenv` 裸读，无集中校验、无类型。配置项已增至 AMAP/LLM/CELERY/WEATHER/PROMETHEUS/SKIP_DB 多组，裸读难维护。

> 处置：迁移 `pydantic-settings`——**已在 pyproject 依赖中，零新依赖**，集中管理默认值 + 类型 + 校验。

### 3. chat.py 编排遗留 dead code（低，新增）

LangGraph 接管编排后，`chat.py` 的 `chat_stream` / `chat_complete` / `mock_stream_chat` / `MOCK_MODE` 均无调用方（仅定义 + 从 `agent/__init__.py` 导出），实际被用的只剩 `build_chat_messages`。planner.py（@placeholder 未接线）同理待决。

> 处置：清理 chat.py 死代码（保留 build_chat_messages + MOCK_MODE 或整体迁至 orchestrator）；planner.py 按 ADR-008 §9 激活为 PlanAgent 或移除。

### 4. agent 包收尾（低）

编排独立后 `agent/` 剩余：chat.py（消息构建）+ orchestrator.py（编排）+ commentator.py + planner.py（未接线）+ tools/（叶子）。职责比轴 1~6 时清晰，剩余主要是 #3 的清理。

### 5. `domain/` 覆盖不全（中）

只有 LLMService 和 WeatherService 两个 Protocol。行程 / 景点 / 任务这些**业务领域对象**仍以 dict 形态散在 engine/api/celery 之间，类型弱、无契约。防腐层只保护了「换 LLM/天气」两个点，保护不了「换编排/换存储」。当前 domain 是**战术防腐**而非**战略领域层**。

> 处置：按需渐进，随业务对象稳定后再提纯为协议类型。

### 6. `celery_app.py` 是隐式 hub（中）

建表 + 发任务 + 执行引擎 + 解决 asyncpg 跨 loop，又被 routes.py 和 tools/plan.py 同时依赖。循环导入靠延迟 import 压住，但**职责过重的单模块是未来重构最痛的起点**。

> 处置：观察，若任务类型增加（suggest/plan/其他），拆出**任务分发注册表**。补充说明：
> - 提交侧已解耦：routes.py 与 tools/plan.py 只 import `submit_task`（task_type 参数化通用入口），不直接引用 run_plan_task，新增任务类型无需改调用方。
> - 真正分发点在 worker 侧 `_execute_task` 的 `is_suggest` if/else；任务类型增至 3+ 时改为 `{task_type: async 执行函数}` 注册表，而非 routes 侧注册表。
> - 拆分时注意：`@celery_app.task` 注册机制要求任务模块被 import，tasks/ 包拆出后须保证 `tasks/__init__.py` 被 celery_app 或 worker 加载，否则报任务未注册。

### 7. 契约测试缺失（持续）

engine 层 42 个测试扎实，但 api/celery/mcp 层零自动化测试，端到端全靠手动脚本。**本次新增编排层（orchestrator.py）后，编排逻辑也无自动化测试**（仅靠 mock 手测）。防腐层（domain/LLMService）的**核心价值恰恰需要契约测试锁定**——「换实现行为不变」没有测试验证就是空话。

> 处置：补契约测试覆盖 api/celery/mcp/orchestrator 四层（ADR-008 §8 换框架纪律的落地前提）。

### 8. 任务无重试机制（低）

`task_acks_late=True` 但无 autoretry。驾车 API 偶发失败直接 `failed`，用户只能重新提交——错峰重试缺失。

> 处置：任务失败重入 broker 或标记 retryable，按需实现。

### 9. 类型三处手工同步（中）

`backend/typedefs.py`（后端内部）+ `frontend/src/types.ts`（前端）+ `docs/structure/data.md`（文档）描述同一批 PlanResult 结构，全靠手工对齐，漂移风险真实存在。

> 处置：中长期以 OpenAPI 生成 / 单一 schema 源驱动，手工同步为过渡态。

### 10. 驾车 API 无后端缓存（低）

同城市同景点的 cost_matrix 每次全量拉 40s，除前端 store 显式复用外无后端缓存层（opentime2 哈希缓存此前判定暂不做）。

> 处置：高德结果按 (city, 景点集) 缓存到 Redis，独立于轴 4 的并行拉取策略。

### 11. API 无版本化（观察项）

全部挂 `/api/` 无 `/api/v1` 前缀。单服务自用、无外部消费者，**当前可接受**；若开放对外或出现破坏性变更需求再引入。

## 处理优先级

| 优先级 | 项 | 理由 |
|--------|-----|------|
| P0（立即） | Numba 内核去重（#1） | 小改动、零风险、消除改一忘一隐患 |
| P0（立即） | config 迁移 pydantic-settings（#2） | 依赖已装零新增，集中配置可维护性 |
| P0（立即） | chat.py 编排遗留 dead code 清理（#3） | LangGraph 接管后的收尾，零风险 |
| P1（持续） | 契约测试补 api/celery/mcp/orchestrator 层（#7） | 换框架纪律的前提，随改动补 |
| P1（按需） | planner.py 激活或清理（#4） | 配合 PlanAgent 接入时机 |
| P2（按需） | domain 覆盖业务对象（#5）/ celery hub 拆分（#6）/ 任务重试（#8）/ 类型单一来源（#9）/ API 缓存（#10） | 随业务增长自然触发 |
| 观察 | API 版本化（#11） | 无外部消费者前不动作 |
