# ADR-011: 实时通道选型——SSE 维持，WebSocket 暂不引入

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-08-27 |
| 标签 | 实时通道 / 选型 |
| 复审触发 | 出现服务端主动推送 / 双向低延迟 / 高并发长连接需求时 |
| Supersedes | 无 |

## 状态

**Accepted**。

## 执行摘要

- 在「SSE vs WebSocket」的实时通道选型中，选择维持 **SSE（Server-Sent Events）**。
- 理由：当前实时通信全为**单向流式**（LLM token 流 / chat SSE / 任务状态轮询），SSE 足够且更简单、HTTP 代理友好、EventSource 自动断线重连、无连接状态管理。
- 代价：单向（无服务端主动推/双向）、每路一条 HTTP 连接、二进制需额外处理。

**Y-Statement**：在「单向流式（LLM token、任务轮询、chat）」的上下文下，我们选择 SSE，以换取简单、代理友好与自动重连，接受「单向、每路一条连接、无双向低延迟」。

## 背景

TravelPal 的实时数据分三类：/api/chat 的 SSE 流式对话（LangGraph 产出事件）、suggest/plan 的异步任务状态（前端轮询 /api/tasks/{id}）、POI/行程结果回传。均为**服务端单向 → 客户端**的流式/轮询，无服务端主动推送需求。需在 SSE 与 WebSocket 间定实时通道。

## 决策

1. **维持 SSE**：/api/chat 用 StreamingResponse + SSE 事件流（content/tool_status/tool_result/error/done）。
2. **任务状态走轮询**：suggest/plan 提交返回 task_id，前端轮询 /api/tasks/{id}。
3. **不引入 WebSocket**：仅在复审条件触发时评估；单向流式无需双向通道。
4. **SSE 代理配置**：关闭 Nginx 缓冲（X-Accel-Buffering: no）、keep-alive，保证流式即时。

## 备选方案

### 方案 A：WebSocket（双向长连接）

建立双向持久连接，服务端可主动推、双向低延迟。

**否决**：其价值在服务端主动推/双向/单连接多路复用；当前全为单向流式，用不到；连接/状态管理、跨域、旧代理兼容成本高，不是"升级"而是换场景。

### 方案 B：HTTP 长轮询 / 轮询 + SSE 混合

用长轮询替代或混用 SSE。

**否决**：轮询协议更复杂、延迟与开销更大；SSE 已覆盖单向流式且自动重连，无必要再混入长轮询。

## 后果

**正面**：

- 实现简单、HTTP 代理友好、无连接状态管理。
- EventSource 自动断线重连。
- 与 Cookie+Session（ADR-010）拼合为最自洽的栈。

**负面**：

- 单向（无服务端主动推、双向交互）。
- 每路一条 HTTP 连接（HTTP/1.1 并发连接数受限，需注意 keep-alive/HTTP2）。
- 二进制传输需额外处理（当前无此需求）。

**中性**：

- 与鉴权通道解耦，未来可单独切换到 WebSocket（触发时）。
- 任务状态用轮询而非 SSE（避免每任务一条长连接）。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 代理缓冲导致流式延迟 | token 不即时 | Nginx 关缓冲 X-Accel-Buffering: no + 禁用代理缓冲 |
| 每路一条连接高并发 | 连接数压力 | 任务状态走轮询减少长连接；必要时 HTTP/2 keep-alive |
| SSE 断线重连抖动 | 事件丢失/重复 | EventSource 自动重连 + 事件 id 幂等处理 |
| 单向覆盖不了主动推 | 未来体验受限 | 记录为复审条件，触发时切换 WebSocket |

## 复审条件

- 出现**服务端主动推送**（如行程变化提醒）、**双向低延迟**（如协作/Agent 主动打断）、**高并发长连接**（单连接多路复用）时，再评估 WebSocket。
