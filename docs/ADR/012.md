## 状态

**✅ 已采纳**——作为 LLM 框架生态的落地边界基线，配合 ADR-008 组件化克制理念持续演进。

## 背景

LangChain 生态含九层组件（Models / Prompts / Retrievers / Chains / Agent / Memory / tools / callbacks / Indexes & Vector Stores）。本项目在未引入 langchain 主包的前提下逐层对照落地，需要一份**明确的边界盘点**：哪些层值得自写（更轻、可控）、哪些层引入轻量框架（langgraph）、哪些层留占位（重生态按需再引）、哪些明确不引入——防止未来盲目堆砌框架。

核心原则（ADR-008 §7 组件化理念）：**框架是手段不是目的**，只引用框架特定功能，用防腐层 + 依赖倒置解耦。

## 九层逐条对照

| 层 | 生态默认形态 | TravelPal 实际落地 | 结论 |
|----|-------------|-------------------|------|

## 三类边界汇总

- **已落地（手写/轻量替代）**：Models、Prompts、Chains（LangGraph）、tools、callbacks（prometheus 埋点）
- **占位/规划**：Retrievers（BM25 在用，LlamaIndex/hybrid 占位）、Memory（未做，规划 checkpointer+PG）、DSPy（占位）
- **明确不引入**：langchain 主包、langsmith、langserve、CrewAI、Django

## 关键决策

1. **自写优先，选择性引框架**：Models / Prompts / tools / 埋点四层自写——它们简单、可控、零框架泄漏，引入框架反而多一层防腐翻译。但「自写优先」不是「一律自写」：当框架满足「白盒可读 + 实现简单 + 依赖少 + 轻量 + 确有大用」时引入（如 langgraph 之于图编排、markdown-it 之于 md 解析——单文件、零依赖、~30KB，干的是自写最脏的活）。判断权在「引入成本 vs 手写成本」，不在绝对教条。
2. **编排必须引框架**：对话编排（多轮工具循环 + 流式）是唯一值得引框架的层，选 langgraph（图状态机 + 原生多 Agent 演进），只依赖 langchain-core。
3. **重生态只留占位**：DSPy / LlamaIndex / 向量库——当前 BM25 已够用，真实需求出现（prompt 调优 / 语义检索）再按需实现，用占位文件守住目录结构（ADR-008 轴 7）。
4. **Agent 自主执行不引入**：ReAct 骨架已有但保持轻量，不扩展——产品哲学（ADR-004 铁律 1「Agent = 陪玩，不是决策者」）决定人机协同优先。

## 边界判断：何时从手写迁移到框架

「自写 vs 框架」的边界不是感觉，而是**可量化、可观测**的信号。判断方法分三层递进。

### 通用判断流程（任何层适用）

```
① 有真实需求吗？    → 用户行为/查询数据证明缺这个能力（不是「觉得该加」）
② 手写层现在稳吗？  → 当前实现「几乎不动」→ 框架永远不划算；改动频繁才考虑
③ 框架带来的是？
   ├─ 同能力的封装（自写也能做） → 不引，除非维护成本爆炸
   └─ 新能力（向量语义/图中断恢复/多模型路由） → 需求出现才引
④ 度量触发          → 先量后换：命中率 / 改动频率 / 错误率，数字说话
```

核心准则：**自写能解决 80% 需求且 80% 时间稳定，就不引**——先看框架解决的是「低频 edge case」还是「高频但手写难做的需求」：前者特判处理，后者才引。补充例外：**纯「脏活」框架**（如 md 解析/时间格式化等无业务逻辑、无防腐层负担的通用能力）不受此限——只要白盒、轻量、依赖少，直接用（markdown-it 先例）。

### 各层触发信号表

| 层 | 现状 | 明确触发信号（可观测） | 到点后怎么换 |
|----|------|----------------------|-------------|
| Models | 手写，3 种调用形态 | LLM 调用形态从 3 种增到 10+（embedding/rerank/vision）；需要 A/B 测模型或模型路由 | 先加多实现+路由，未必引 langchain |
| Prompts | 手写集中管理 | prompt 需要版本化/回滚/A-B 测试（改一次管半年 → DSPy 是负资产） | DSPy 占位此时才激活 |
| Retrievers | BM25 零依赖 | 用户出现语义相似查询（「找类似故宫的」），且 BM25 top-3 命中率实测 < 70% | 先度量 → hybrid_retriever 按需求实现 |
| Memory | 未做 | 跨轮持久化成真实需求（「记住我上次的偏好」） | 先自写 PG 消息表；只有「对话中断精确恢复」才上 checkpointer |
| tools | 5 工具手写 | 工具间出现复杂链式组合（A 输出是 B 输入） | 再评估 @tool 框架化 |
| 编排 | 已引 LangGraph | 单 Agent 上下文超限（历史压缩失效）/ 误调工具率上升 | 拆子图 / Supervisor |

### 翻译层成本陷阱

引入框架后，「手写逻辑」与「框架逻辑」会长期并存（防腐层翻译代码），翻译层本身要维护。因此：

- **占位优于提前引**——占位零翻译层成本
- **每引一个框架 = 多一层防腐翻译**（ADR-008 §7 反方观点），判断时问自己：翻译层成本多久回本？

### 落地结论

真正的边界不是「手写 vs 框架」，而是**「手写能证明自己够用，就不换」**。判断权在度量不在感觉：

- BM25：用命中率说话
- Memory：用「是否需要图级中断恢复」说话
- Models：用「调用形态是否爆炸」说话
- 编排：用「单 Agent 决策质量是否下降」说话

每层都留有明确升级路径（本 ADR 触发信号表 + ADR-008 §8 换框架纪律 + 占位文件），「自写」是有退路的第一选择，不是死路。
