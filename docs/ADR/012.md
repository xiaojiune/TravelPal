# ADR-012: 手写轻量架构 + 选择性引框架（LangChain 生态边界）

## 元信息

| 项 | 值 |
|----|----|
| 作者 | xiaojiune |
| 生效日期 | 2026-08-06 |
| 标签 | `LLM 框架 / 依赖边界` |
| 复审触发 | 任一层的可观测触发信号出现时（见复审条件） |
| Supersedes | 无 |

## 状态

**Accepted**。

作为 LLM 框架生态的落地边界基线：默认自写，当框架满足"白盒可读 + 实现简单 + 依赖少 + 轻量 + 对当前问题确有大用"时才引入（如 langgraph 之于编排、markdown-it 之于 md 解析）。

## 执行摘要

- LangChain 生态含九层组件（Models / Prompts / Retrievers / Chains / Agent / Memory / tools / callbacks / Indexes & Vector Stores）。本项目在不引 langchain 主包的前提下逐层对照落地。
- 原则是"**自写优先，选择性引框架**"：默认自写；当框架满足白盒、轻量、依赖少、确有大用时引入；重生态只留占位；明确不引入 langchain 主包 / langsmith / langserve / CrewAI。
- 编排层是唯一值得引框架的层（多轮工具循环 + 流式），选 langgraph，只依赖 langchain-core。
- 判断权在"引入成本 vs 手写成本"，不在绝对教条；每层都留有可观测的触发信号与升级路径。

**Y-Statement**：在"需可控、轻量、低框架泄漏"的 LLM 应用场景下，我们选择自写优先、选择性引框架，以换取可控与低依赖，接受"部分管线需自写 + 引入层需维护防腐翻译"。

## 背景

LangChain 生态含九层组件。项目在未引入 langchain 主包的前提下逐层对照落地，需要一份明确的边界盘点：哪些层值得自写（更轻、可控）、哪些层引入轻量框架、哪些层留占位（重生态按需再引）、哪些明确不引入——防止未来盲目堆砌框架。核心（组件化理念）：框架是手段不是目的，只引用框架特定功能，用防腐层 + 依赖倒置解耦。

## 决策

### 分层落地对照（路径见组件状态跟踪）

| 层 | 生态默认形态 | TravelPal 落地 | 结论 |
|----|-------------|---------------|------|
| Models | ChatOpenAI 等 | 手写 LLMService 防腐层 + OpenAI 实现（DeepSeek），factory 切换实现 | 已落地 |
| Prompts | PromptTemplate | 手写集中管理，聊天消息注入；DSPy 优化占位 | 已落地 + 占位 |
| Retrievers / Indexes | LlamaIndex / 向量库 | 自研 BM25（零依赖）为当前实现；LlamaIndex / hybrid 占位 | BM25 在用，重生态占位 |
| Chains | LCEL | 引入 langgraph（含 langchain-core），StateGraph 单 Agent 编排 | 已落地 |
| Agent（ReAct） | AgentExecutor | 未套用 langchain Agent 封装；编排条件边自环已是 ReAct 骨架；不在 Agent 自主执行方向扩展（产品哲学：Agent=陪玩非决策者） | 不引入，保留轻量骨架 |
| Memory | langchain.memory / checkpointer | 未实现。规划形态：LangGraph checkpointer + 持久化；Redis 现为 Celery broker | 规划未做 |
| tools | @tool / Tool 注册 | 手写工具注册表（函数类型注解 + docstring 自动生成 schema，与 MCP input_schema 同源）；独立进程挂载 MCP | 已落地 |
| callbacks | BaseCallbackHandler | 手写 prometheus_client 埋点（llm/driving/task/http + /api/metrics），非 langchain callback handler | 已落地 |
| Indexes | 同 Retrievers | 无向量索引；hybrid_retriever 占位 | 同 Retrievers |

### 关键决策

1. **自写优先，选择性引框架**：Models / Prompts / tools / 埋点四层自写——简单、可控、零框架泄漏。但"自写优先"不是"一律自写"：当框架满足"白盒 + 简单 + 依赖少 + 轻量 + 确有大用"时引入（如 langgraph 之于图编排、markdown-it 之于 md 解析——单文件、零依赖、干的是自写最脏的活）。判断权在"引入成本 vs 手写成本"。
2. **编排必须引框架**：多轮工具循环 + 流式是唯一值得引框架的层，选 langgraph（图状态机 + 原生多 Agent 演进）。
3. **重生态只留占位**：DSPy / LlamaIndex / 向量库——当前 BM25 已够用，真实需求出现再按需实现，用占位文件守住目录结构。
4. **Agent 自主执行不引入**：ReAct 骨架已有但保持轻量，不扩展——产品哲学决定人机协同优先。

## 备选方案

### 方案 A：全套引入 LangChain 主包

用 langchain 覆盖 Models/Prompts/Chains/Agent 等各层。

**否决**：框架泄漏大、依赖重、与防腐层抢边界；不是针对当前问题的最小方案。

### 方案 B：自写优先、选择性引框架（采纳）

**否决**：无——采纳本方案。

### 方案 C：全自写，不引任何框架（含编排）

编排也用自写状态机。

**否决**：编排（多轮工具循环 + 流式 + 检查点）自写成本高、难维护，langgraph 恰好是"轻量、白盒、确有大用"的例外。

## 后果

**正面**：

- 低依赖、低框架泄漏，换模型/重构爆炸半径小。
- 各层留有可观测触发信号与升级路径。

**负面**：

- 部分管线需自写，前期工作量更大。
- 引入层需维护防腐翻译代码。

**中性**：

- "自写"是有退路的第一选择，不是死路。

## 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 自写层长期无人维护 | 落后于生态 | 以可观测触发信号决定是否迁移 |
| 引入框架增加翻译层 | 翻译层本身要维护 | 占位优于提前引；问"翻译成本多久回本" |
| 依赖 langgraph 停更 | 编排层失效 | 状态转移层与框架解耦，替换成本限 Adapter |

## 复审条件（各层可观测触发信号）

- **Models**：LLM 调用形态从 3 种增到 10+（embedding/rerank/vision），或需模型路由 → 评估多实现+路由。
- **Prompts**：prompt 需版本化 / 回滚 / A-B 测试 → DSPy 占位才激活。
- **Retrievers**：用户出现语义相似查询，且 BM25 top-3 命中率实测 < 70% → 先度量再实现 hybrid。
- **Memory**：跨轮持久化成真实需求 → 先自写持久化；仅"对话中断精确恢复"才上 checkpointer。
- **tools**：工具间出现复杂链式组合 → 再评估 @tool 框架化。
- **编排**：单 Agent 上下文超限 / 误调工具率上升 → 拆子图 / Supervisor。
