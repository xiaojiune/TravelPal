## 状态

**✅ 已采纳**——作为前端 UI/UX 的可复用设计模式基线，配合 ADR-002 前端选型与 ADR-009 Naive UI 迁移持续演进。

## 背景

首页主页面 UI/UX 重设计完成。复盘过程发现**前端难度不在语法而在 UI/UX 设计**：一次视觉调整牵扯大量状态逻辑（activeSection 手风琴 / activePoiCard 展开 / activeEditField 编辑态 / 三绿 / warnCount），AI 编程亦然。为沉淀方法论、避免后续页面重复踩坑，将设计模式与外部 AI 助手建议的方案取舍落档。

## 核心发现：设计从用户心智反推

视觉决策不是孤立样式，而是与状态逻辑强耦合。首页重设计的本质是把「用户完成三件事」的流程，翻译成可观测、可推进的状态机：

```
用户心智            →  状态机
填了城市           →  cityGreen
酒店拉取成功       →  hotelGreen
添加了景点         →  spotsGreen
三绿齐备           →  allGreen → 生成按钮青绿
景点参数没填全     →  warnCount !N
```

结论：**先定义状态语义，再设计视觉反馈**——视觉只是状态的投影，状态不明则视觉必然反复返工。

## 已沉淀的可复用设计模式

| 模式 | 说明 | 复用场景 |

## 关键决策

1. **状态语义先于视觉**：视觉是状态的投影，先定状态机再设计反馈，避免反复返工。
2. **能自写不引组件库**：A2UI 等声明式库不引 renderer——无 Vue 官方实现（自写即违反原则），且 ToolResultCard/SchemaFormCard 已构成自写 mini-catalog（延续 ADR-012 原则）。A2UI 仅作协议观察（见下）。
3. **编辑即确认**：删除「确认按钮」概念，改为即时回写 + 短反馈，减少确认摩擦。
4. **黄!N 而非红!**：待补充用黄 + 计数表达「还差什么」，红色留给真正的错误（生成按钮未就绪）。
5. **氛围动画克制**：决策工具场景，情感化动画是噪音，仅保留状态切换微动效（poi Transition / folder Transition）。

## 有增量价值的待评估项

- **方案 7 地图优先**：PlanPage 从「行程表为主」转向「地图为主 + 浮动面板」，动效成本高，收益待验证。
- **方案 8 时间线主视图**：按时间线（而非按天表格）展示行程，与 SchedulePanel 迁移成本高，暂缓。

两者均属 PlanPage 范畴，作为 v1.1 候选，需先明确收益再投入。

## A2UI 预留观察（2026-08-08 调研后补充）

A2UI（Agent-to-User Interface）是开源声明式 UI 协议：agent 发 JSON 描述 UI，客户端用自有组件库渲染（「safe like data, expressive like code」）。四消息流（createSurface / updateComponents / updateDataModel / deleteSurface）+ 双向 RPC（actionResponse / callFunction），传输无关（官方 binding 含 MCP）。

**判定：renderer 不引，协议观察。** 理由：
1. 官方 renderer 为 lit / react / angular / flutter / markdown / web_core——**无 Vue**，接入需自写 Vue renderer，恰是 ADR-012「能自写不引框架」反对的。
2. v1.0 为 release candidate（2026-06-08 更新），未稳定；v0.9.1 才是稳定生产版。
3. 与 ToolResultCard（四型富卡片）+ SchemaFormCard（OpenAI parameters 驱动表单）构成的自写 mini-catalog 能力重叠。
4. 当前确定性工具流（固定 schema）价值有限，A2UI 价值在 agent 动态生成 UI。

**增量窗口（预留）**：A2UI over MCP——当 MCP Client / 外部 AI 集成到来时，工具输出（如 get_plan 结果）编码为 A2UI payload，让外部客户端渲染富 UI（分享站 / 外部集成差异化能力）。**触发信号 = 出现第一个消费 A2UI 的外部客户端**，届时仅需在 MCP Server 侧增加一个输出适配，不动前端。
