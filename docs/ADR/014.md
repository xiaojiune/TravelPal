## 状态

**✅ 已采纳**——编排层维持 LangGraph，不引入 PydanticAI；其结构化输出能力通过防腐层自建 helper 吸收，符合 ADR-012「能自写不引框架」原则。

## 背景

用户提问「LangGraph vs PydanticAI，编排层选型是否要换」。PydanticAI 是 Pydantic 团队推出的轻量 Agent 框架，以结构化输出为卖点（`result_type=Model` 自动解析/校验/失败重试 re-prompt）。需评估是否值得替换现有 LangGraph 编排层，或将 PydanticAI 能力吸收进项目。

## PydanticAI 强项

1. **结构化输出杀手锏**：`result_type=Model` 自动解析/校验，失败自动重试 re-prompt，无需手写 JSON 解析。
2. **Deps 依赖注入**：类型化依赖注入，工具可声明式获取上下文。
3. **tools + result 全 Pydantic 类型链**：从工具 schema 到输出校验全类型化。
4. **轻量单文件**：单模块即可跑通 agent 流程，上手成本低。

## 对项目的劣势（不引入框架的理由）

| 维度 | 对比 |
|------|------|
| 控制流 | 我们是 Router-Executor 循环（LLM 决策 → 工具执行 → 回填 → 再决策），LangGraph 条件边 + 自环是原生表达；PydanticAI 控制流弱（偏线性 tool-call 循环） |
| 多 Agent 演进 | ADR-008 §9 远期 Supervisor / Hierarchical teams（LangGraph 原生支持）；PydanticAI 无图级多 Agent，演进路径锁死 |
| 防腐层边界 | 与 domain/LLMService 防腐层抢边界（都想要「模型调用的唯一入口」），侵入改造大 |
| 成熟度 | 0.x 快速演进，API 不稳定，团队已有 LangGraph 落地经验 |

## 关键洞察：PydanticAI 提醒的真缺口

PydanticAI 的价值点不在框架本身，而在它暴露的一个**真实缺口**：**「LLM 输出不可信，需结构化 + 校验 + 失败重试」**。项目拆成两个场景吸收：

- **场景一：文本 → 模型（parse_structured）**。`LLMService.complete()` 返回原始文本，结构化解析分散在调用方（如 `poi.py` 手写 `json.loads` 解析营业时间 JSON）。正确做法：用 Pydantic v2 在 domain 防腐层自建轻量 `parse_structured` helper——传入目标模型 + LLM 输出，自动解析/校验/失败重试 re-prompt，收敛到单一实现。
- **场景二：工具参数容错 + 失败重试**。LLM 误调工具（参数缺失/类型错误，如联调中把 remove_poi 参数名错用给 add_poi）时，编排层不应中断整轮对话，而应回填错误让 LLM 看到后自我修正重调。已实施：`orchestrator._tools_node` 对工具调用包 try/except，异常转 `{"error": ...}` 回填 tool 消息（PydanticAI re-prompt 重试的手写等价实现）。

两场景都遵循：
- 保留 LangGraph 控制流 + LLMService 防腐层（现状零重构）
- 吸收 PydanticAI 最核心的结构化输出/容错能力
- 延续 ADR-012「能自写不引框架」原则

## 决策

1. **编排层维持 LangGraph**：Router-Executor 与多 Agent 演进路径均正确，无替换动机。
2. **不引入 PydanticAI 框架**：控制流弱、演进锁死、边界冲突、成熟度低，四维度均不支持。
3. **自建「LLM 输出结构化 + 容错」能力**（两场景）：场景二工具参数容错已实施（orchestrator._tools_node try/except 回填 error）；场景一 `parse_structured`（Pydantic v2 驱动，失败重试）在 `domain/llm_service.py` 自建，收敛 poi.py 等处的手写 `json.loads`，列为 ADR-014++ 🚧 待实施项（beta 后）。
