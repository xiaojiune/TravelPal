本目录存放 TravelPal 的架构决策记录（Architecture Decision Record）。本文档定义 ADR 的**写作规范**与**生命周期管理**，并提供现有决策的**索引**。

## 一、体系说明

- **ADR = 决策记录**：只记录「选了什么、为什么选、代价是什么」，不记录实施细节。append-only 活文档——决策演进用新条目/新 ADR 追加，不改写历史。
- **一文档一重大决策**：每篇 ADR 聚焦一个架构决策；关联度极高的子主题允许同文档分节（如 ADR-012「九层对照 + 边界判断」）。
- **新增 ADR 必须使用 [TEMPLATE.md](./TEMPLATE.md)**，章节结构与本文档「标准章节结构」一致。

## 二、生命周期状态

ADR 本身有生命周期，与决策内组件的实施状态是**两套体系**：

| 状态 | 含义 |
|------|------|
| Proposed | 提议中：方案提出，尚未定稿 |
| Accepted | 已采纳：决策定稿，作为当前事实 |
| Deprecated | 已废弃：决策不再适用，但未被替代 |
| Superseded | 已替代：被后续 ADR 取代（标记 `Superseded by ADR-XXX`） |

> 组件实施状态（✅ 已落地 / 🚧 占位规划 / ⏸ 不引入）记录在正文「组件状态跟踪」节，表示**决策内各组件的落地进度**，与 ADR 自身的生命周期状态无关。

## 三、标准章节结构

对应 [TEMPLATE.md](./TEMPLATE.md)，共 13 节：

| 章节 | 写什么 |
|------|--------|
| 元信息 | 作者 / 生效日期 / 标签 / 复审触发 / Supersedes（用表格，不用 YAML，Sphinx 兼容） |
| 状态 | 生命周期状态（默认 Proposed） |
| 执行摘要 | 3-5 行电梯演讲 + Y-Statement 一句话决策，30 秒抓核心 |
| 背景 | 为什么做（Context），绑定前置约束与产品哲学 |
| 决策 | 做了什么——正文**不含文件路径**（路径归「组件状态跟踪」验证列） |
| 备选方案 | ≥2 个被否决方案 + 逐一否决原因（必须独立成节） |
| 后果 | 独立成节：正面收益 / 负面代价 / 中性风险三类显式列出 |
| 风险与缓解 | 依赖风险、占位腐烂、版本升级等 + 规避方案 |
| 复审条件 | 何时需重新审视本决策（可量化触发信号优先） |
| 组件状态跟踪 | ✅/🚧/⏸ 状态表，「验证」列放文件路径锚点 |
| 落地与校验 | （可选）CI 检查项，保障决策长期落地不被破坏 |
| 交叉引用 | 双向链接：本 ADR 引用的，以及反向引用本 ADR 的 |
| 修改记录 | 日期 + 变更 + 动机 |

## 四、写作约定

1. **标题决策陈述式**：直接陈述结论（如「采用手写轻量级架构替代 LangChain 全栈框架」），不用「对照 / 探讨」等过程词。存量 ADR 保留旧式标题，不回溯改名。
2. **正文与实施细节分离**：决策正文聚焦「做什么 / 为什么」，文件路径、函数名归「组件状态跟踪」验证列或交叉引用——ADR 不随代码重构频繁改动。
3. **决策理由充分**：每个选择必须写「为什么不选其他」，这是 ADR 的核心价值。
4. **可量化触发机制**：边界判断、迁移条件用可观测指标（如「BM25 top-3 命中率 < 70%」）而非主观感受。
5. **交叉引用双向性**：A 引用 B 时，B 也应反向链接 A（或在修改记录注明），保证决策图谱连通。
6. **修改记录完整**：每次变更记「日期 + 变更内容 + 动机」；修改人可省（个人项目）。
7. **状态同步**：决策内的组件状态（✅/🚧/⏸）随实施进展实时更新「组件状态跟踪」节。
